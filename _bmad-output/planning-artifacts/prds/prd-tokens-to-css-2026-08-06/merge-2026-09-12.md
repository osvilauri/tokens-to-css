# Multi-file merge — input and merge design

Input to the PRD revision the survey has been demanding since Epic 4 closed: of
the 58 corpus files that still failed, **53 failed on a reference to a token
defined in a sibling file**. This document settles how several documents become
one, and stops there — which context a modifier resolves to is chosen, not
enumerated, so themes remain the epic after this one.

Resolver field names, `resolutionOrder` semantics and context defaults below were
read from the DTCG Resolver Module (2025.10) and from the seven manifests in the
corpus on 2026-09-12, not from memory.

## The finding that shaped it

Every design system in the corpus ships a **resolver manifest** — the corpus
README lists `<system>.resolver.json` as the import for each one. Merge order is
therefore not something this library has to invent a convention for: it is
declared, in a standard, by the people who wrote the tokens. Three consequences
run through every decision below:

- **The list is the primitive; the manifest is a dialect of it.** A manifest
  expands to an ordered list of sources and nothing else. That layering is the
  same one the token dialects already use — the pure thing underneath, the
  published format on top — and it means a team with five files and no manifest
  is a first-class caller, not a workaround.
- **Later wins, because contexts exist.** A manifest's whole purpose is that
  `theme=dark` is applied over the base. A merge that refused to let a later
  source redefine a path would refuse the format's central move.
- **A source may legitimately appear twice.** GitHub Primer lists
  `light.tokens.json` in `sets/base` *and* in `modifiers/theme/light`. Under
  last-wins it is applied twice with identical values, 98 times over. Any rule
  that treats "this path was defined before" as an anomaly fires 98 times on a
  perfectly valid published manifest.

## Where the merge happens

**On the internal representation, after each document is normalized on its own.**
Not on the raw JSON.

The merge takes `TokenDoc`s — flat, ordered arrays of `{path, value}` — and
produces one. Each source is read, detected and normalized by the existing
registry, alone, exactly as it is today. Four things follow, and each of them is
the reason not to deep-merge raw JSON instead:

1. **A system may mix dialects.** Per-document detection lets one file be DTCG
   and its neighbour a Style Dictionary legacy export. Merged first, the pair
   would be one document that speaks two dialects, which the registry correctly
   refuses (AD-3, precedence).
2. **Prototype-pollution safety is already solved per document** (AD-9). A raw
   deep merge of untrusted JSON is a second place to get that wrong.
3. **Merging is a path-keyed operation**, and the IR is where paths exist. On
   raw JSON it is a tree walk that has to re-derive what a token node is — the
   one job the normalizers own.
4. **`skipped` composes.** Each document's skips are facts about reading *that*
   document, and concatenate in source order without interpretation.

The merged document is what the alias graph and the collision pass see. That
single sentence is the whole feature: a reference from `bgColor.default` to
`base.color.neutral.6` is resolved against the merged document, so it is not
dangling any more.

### Order in the merged document

**First appearance decides position; a redefinition updates the value in place.**
Emission order is document order (AD-10), and a redefinition is not a new token —
it is the same token, with a later value. Appending it instead would move a
property to the bottom of the stylesheet whenever a theme touched it, and the
diff of a generated file is a thing this product protects.

## Redefinition is not collision

The vocabulary splits, the way *Alias Graph Validation* and *Reference Emission*
were split in the v1 review (§13 / C2):

| | What it is | What happens |
| --- | --- | --- |
| **Redefinition** (new) | The **same token path** defined by more than one source | Later wins. Announced when the value changes. |
| **Name collision** (FR-21, unchanged) | **Different token paths** that emit the same custom-property name | Fatal, `NAME_COLLISION`, as today |

They are not near-misses of each other: one is the merge doing its job, the other
is two tokens fighting over one name in the output. Collision detection keeps
running on emitted names, after the merge, over the merged document — AD-12 is
untouched.

**Only a value-changing redefinition is announced.** Applying the same source
twice, or two sources that agree, changes nothing observable and is reported as
nothing. This is not a convenience: without it, Primer emits 98 announcements
about a file being listed twice in its own manifest, and the announcement becomes
noise to scroll past — which is how a warning stops being read.

Measured on the corpus: **98 identical re-applications, 0 value-changing
redefinitions** across all seven systems under default contexts. The announcement
costs nothing here. It exists for the case that is not in the corpus and is the
obvious way to get a stylesheet quietly wrong: a file added to the list that
shadows a token nobody meant it to shadow.

## What the caller passes

```ts
generateCss(source: string | URL | readonly (string | URL)[], options?)
```

- **One source** — unchanged in every respect, down to the bytes.
- **A list** — merged in order, later wins. Paths and URLs may be mixed; each is
  loaded by the adapter it belongs to, under the same policy as today.
- **A resolver manifest** — one source whose *content* is a manifest. It expands
  to a list and the list is merged. Detected by content, never by filename:
  `resolutionOrder` present at the root, alongside `sets` or `modifiers`.

An **empty list** is refused (`FORMAT_NOT_ALLOWED`): it is a caller bug that would
otherwise surface as "no tokens were recognized", pointing at the documents
rather than at the call.

### The resolver subset accepted here

| Accepted | |
| --- | --- |
| `resolutionOrder` | array of `{"$ref": "#/sets/<name>"}` and `{"$ref": "#/modifiers/<name>"}`, applied in array order |
| `sets.<name>.sources` | array of `{"$ref": "<relative path or URL>"}` |
| `modifiers.<name>.contexts.<ctx>` | array of source refs; **one** context per modifier is applied |
| `modifiers.<name>.default` | the context applied when the caller names none |
| `name`, `version`, `$schema`, `$description` | read and ignored |

| Refused (`FORMAT_NOT_ALLOWED`), by name | Why |
| --- | --- |
| A `$ref` in `resolutionOrder` naming neither a set nor a modifier that exists | it resolves to nothing, and silently applying nothing is how a stylesheet loses half its tokens |
| A context or set whose `sources` contain a `#/…` pointer rather than a file | set composition inside contexts is out of this subset |
| A `$ref` that is an absolute filesystem path | a manifest describes its own neighbourhood |
| A remote manifest whose `$ref` leaves the manifest's origin | the URL guard's reason for existing (NFR3–NFR6) applies to what a document can make the library fetch |
| Nesting: a manifest whose sources include another manifest | one level, decided now; nothing in the corpus does it |

**Refs resolve against the manifest**, not against `baseDir` — a relative `$ref`
is written by the manifest's author, about their own directory, and `baseDir`
belongs to the caller. A remote manifest resolves its refs as relative URLs
against its own URL, same origin only.

**A set declared but never named in `resolutionOrder` is applied to nothing**, as
the spec says, and is **named in the result and in the stylesheet's comment
block**. Apple HIG's manifest declares a `typography` set and never orders it,
which is why that system fails with 11 dangling references and converts whole the
moment the set is included. Silently including it would be inventing a resolution
order the manifest did not state; failing without naming it would send a
developer looking for a missing file that is right there. So: fail, and say what
was declared and never applied.

### Contexts

```ts
options.contexts?: Readonly<Record<string, string>>   // { theme: 'dark', size: 'desktop' }
```

Resolution per modifier, in order: **the caller's choice**, else **the manifest's
`default`**, else **fail** with a new code, `CONTEXT_REQUIRED`, naming the
modifier and listing its contexts.

The last step is the one worth defending. Three of the seven manifests declare
modifiers with no default — Adobe Spectrum (`theme`, `size`), IBM Carbon
(`breakpoint`), Microsoft Fluent (`theme`). A manifest with no default is its
author declining to choose, and picking the first context in document order would
be this library choosing a theme on their behalf and writing it into a file that
ships. The failure is a better product than the guess: it lists the contexts and
the option that selects them, which teaches the whole feature in one message.

**One context per modifier, and one `:root`.** Emitting several contexts as
several selectors is the theming epic, not this one. The line is deliberate:
this epic makes a system *convert*; the next makes it *switch*.

## A token in a non-CSS unit is skipped, not fatal

FR-24 made an unwritable token a skip. The boundary it drew was
`err.code === COMPOSITE_VALUE`, and one rejection that is exactly the same kind of
problem sits outside it: an object-form scalar measured in a unit CSS does not
have (`dp`, `sp`, `pt`), refused in `dialects/values.ts` as `FORMAT_NOT_ALLOWED`.

In the corpus that single rejection is **one token in Adobe Spectrum**, and it
takes **1,578 custom properties** down with it. It is the FR-24 argument, word
for word: one token this library cannot express should not cost the other
fifteen hundred.

**The decision.** A new failure code, `UNSUPPORTED_UNIT`, and the skippable
boundary becomes a **set of codes** rather than one. The code is new rather than
reused because calling a `dp` dimension a `COMPOSITE_VALUE` would be false in the
result, in the comment block and in the docs — and because the boundary being a
*code* is what Epic 4 found to be right when the positional version swallowed
FR-17's own message.

**Malformed object-form scalars stay fatal**, and that is a decision, not an
oversight. A `{value, unit}` missing its `unit` is a broken document rather than
an unsupported one, and the corpus does not contain a single instance — so
widening there would be untested generosity. Revisit when a real file asks.

## What the result and the stylesheet say

`GenerateCssResult` gains two fields, both additive:

```ts
readonly sources: readonly string[]        // what was merged, in order, as resolved
readonly redefinitions: readonly Redefinition[]   // { path, from, to }  — value-changing only
```

The comment block above `:root` — already the place where a conversion says what
it left out — gains a merge header when, and only when, more than one source was
merged: the sources in order, the value-changing redefinitions with the source
that won, and any set a manifest declared and never applied. Same reason as
FR-24's block: the stylesheet is a generated file in a repository, so this
appears in the next pull request's diff rather than only in a return value.

**A single-source conversion emits byte-identical output.** No header, no new
fields in the bytes, `redefinitions` empty, `sources` a one-element array. Every
golden written before this epic stays valid, and that is a fixture, not a hope.

## Public surface delta, and why it is a minor

| Change | Kind |
| --- | --- |
| `source` widens to accept an array | additive — every existing call still type-checks |
| `options.contexts` | new optional field |
| `GenerateCssResult.sources`, `.redefinitions` | new fields on a returned object |
| `UNSUPPORTED_UNIT`, `CONTEXT_REQUIRED` | new codes; adding a code is minor (AD-4) |
| A token in a non-CSS unit: failure → skip | a document that used to throw now converts |

The last row is the only one worth a second look, and it is the same shape as
FR-24 itself: input that used to fail now succeeds, and nothing that used to
succeed produces different bytes.

## Fixtures

The corpus gains a fourth category, because `accept/`, `reject/` and `partial/`
all describe **one** input document:

```text
fixtures/merge/<case>/
  sources.json        # ordered list of the inputs, relative to the case directory
  <input files>       # or manifest.resolver.json + the files it names
  expected.css        # golden, byte-compared
  expected.json       # { tokenCount, sources, redefinitions, skipped }
```

Cases frozen with this epic: a plain two-file merge; a cross-file reference; a
value-changing redefinition; an identical re-application that announces nothing;
a mixed-dialect pair; a manifest with sets only; a manifest with a modifier and a
default; a manifest with a modifier and no default (`CONTEXT_REQUIRED`); a
manifest with a declared-but-unordered set; a remote `$ref` leaving its origin
(reject); an empty list (reject); and a single-source conversion proving byte
identity.

## What this does not do

- **Themes.** One context per modifier, one `:root`. Several contexts as several
  selectors is the next epic, and it is the reason this one stops where it does.
- **Directory or glob sources.** FR-1 refuses them and continues to. The corpus
  is the argument: Primer's directory holds 61 files in which `dark` and `light`
  define the same paths, so "merge everything here" would produce a last-wins
  stylesheet nobody asked for. A list is explicit; a glob is a guess.
- **Embedded references** — `"inset 0 0 0 {borderWidth.thin}"`. Three of them
  block GitHub Primer's 1,458 properties, which makes them the next measured
  blocker after this epic and a poor passenger inside it: AD-20 says a value is a
  reference only when the whole string is one, and amending that is its own
  design.
- **Nested manifests**, set composition inside contexts, and `$ref` pointers into
  other documents' internals.
- **Caching across sources.** Fifty-one files parse in 5 ms; there is nothing
  here to optimize yet.
